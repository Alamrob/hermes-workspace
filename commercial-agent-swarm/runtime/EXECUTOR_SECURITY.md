# Hermes executor security boundary

The broker and Hermes executor are separate trust zones. Broker composition may own the PostgreSQL, approval, mail and webhook capabilities, but must depend only on `ExecutorPort`; it must not instantiate `HermesExecutor` or receive `CUSTOM_API_KEY`. Executor composition owns `CUSTOM_API_KEY` and the immutable profile seed, but must not receive database, mail, Telegram, Docker, SSH or host credentials. A deployment transport between these ports is intentionally outside this local-runtime change.

The executor launcher runs as a dedicated root-owned adapter only long enough to copy a root-owned, read-only seed, transfer the ephemeral copy to UID/GID `10000`, and spawn that identity. Its Linux capability bounding set should contain only `CAP_CHOWN`, `CAP_SETUID`, `CAP_SETGID` and `CAP_DAC_OVERRIDE`; the last capability is retained only so the adapter can remove the child-owned `0700` home, and the set is cleared after cleanup. It does not need `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, Docker socket access or host mounts. The ownership preparer rejects symlinks in the copied seed. The child receives exactly the non-secret runtime variables `HERMES_HOME`, `HOME`, `LANG`, `PATH` and the single credential `CUSTOM_API_KEY`. The temporary home is unique per assignment and is recursively removed on success, malformed output, process error or timeout.

The adapter invokes only `hermes -p <closed-profile> --cli chat -q <prompt>`, with `shell: false`. Prompts are single argv data values. Deployment must not add `--oneshot`, `--yolo`, `--accept-hooks`, delegation, profile/model/provider/tool overrides, inherited environment variables or concurrent execution. The checked-in executor envelope schema is closed; only a validated envelope reaches the broker, which alone computes the canonical artifact SHA-256 and persists it.
